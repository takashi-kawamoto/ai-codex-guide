CODEX / AGENTS.MD

CodexのAGENTS.md一覧

まず用意したいAGENTS.md

プロジェクト用の基本形

<project>/AGENTS.md

記載例

  • # Project
Python + FastAPI application.

# Validation
Test:
pytest tests/
Lint:
ruff check .

# Do Not
- Do not force push.
- Do not modify .env files.

使いどころ・ポイント

  • リポジトリのルート直下に置く
  • Codexは作業開始時にまず読み込み、以降の判断の前提にする
  • 最初は数行から始め、運用しながら育てる

AGENTS.mdは、新しく入ったメンバーに最初に渡す「プロジェクトの取り扱い説明書」と考えると書きやすくなります。

グローバルAGENTS.md

~/.codex/AGENTS.md

記載例

  • # Personal Defaults
- Use concise explanations.
- Avoid risky operations.
- Follow my preferred language and response style.

使いどころ・ポイント

  • 複数のプロジェクトで共通の個人ルールを書く
  • プロジェクト側のAGENTS.mdがあれば、そちらが優先される

「グローバルで土台を作り、プロジェクトごとの差分だけ追加する」という2段構成で管理できます。

書き方のテクニック

検証コマンドを書く

テスト・ビルド・Lint

記載例

  • # Validation
Test:
pnpm test
Build:
pnpm build
Lint:
pnpm lint

使いどころ・ポイント

  • 推測ではなく、実際のコマンドをそのまま書く
  • コード変更後にCodex自身がテストを実行・修正しやすくなる

毎回「テストしてください」と指示しなくても、検証まで進めてくれるようになります。

禁止事項を書く

安全設計

記載例

  • # Do Not
- Do not force push.
- Do not modify .env files.
- Do not touch authentication secrets.

使いどころ・ポイント

  • 「やって良いこと」より「やってはいけないこと」を優先して書く
  • 安全に関わる内容は箇条書きで目立たせる

推奨ルールは状況によって無視されることがある一方、禁止ルールは明確な境界線として強く働きます。

モノレポでの階層配置

ルート ＋ サブディレクトリ

構成例

  • repository/
├─ AGENTS.md        # 全パッケージ共通のルール
├─ web/
│  └─ AGENTS.md     # Web固有のルール
└─ api/
   └─ AGENTS.md     # API固有のルール

使いどころ・ポイント

  • ルートには共通の規約と禁止事項を書く
  • 編集中のファイルに最も近いAGENTS.mdが優先される

ルートの内容を土台に、サブディレクトリ側で必要な部分だけを追加・上書きできます。

AI向けに短く書く

命令形 ＋ 具体例

記載例

  • # Rules
- Run tests after modifying code.
- Do not force push.
- Do not edit .env files.

# Good
pnpm test
# Bad
Run whatever test command seems appropriate.

使いどころ・ポイント

  • 長い背景説明より、短い見出しと命令形で書く
  • 良い例・悪い例を並べて誤解を減らす

READMEは人間向け、AGENTS.mdはCodex向けです。長く書くより、誤解なく短く伝えることを優先します。

AGENTS.mdの基本

AGENTS.mdは、Codexに「何をどうやるか」を伝える指示書です。どこまで操作を許可するかは承認・サンドボックス、Codex自体の動作はconfig.tomlで設定します。/initを使うと、既存プロジェクトを調べてAGENTS.mdのたたき台を作成できます。AGENTS.mdが長いと毎回のトークン消費が増えるため、短く保つことも大切です。

CODEX / CONFIG.TOML

Codexのconfig.toml設定一覧

モデルと推論

モデルを固定する

model

設定例

  • model = "<使用するCodex対応モデル>"

使いどころ・ポイント

  • 起動のたびに同じモデルを使い、回答品質の土台を安定させる
  • 別のモデルを試したいときだけ書き換える

モデルを指定しないと、その時点の既定モデルで動作するため、日によって回答の質が変わる可能性があります。

推論の深さを切り替える

model_reasoning_effort

設定例

  • model_reasoning_effort = "medium"
plan_mode_reasoning_effort = "high"

使いどころ・ポイント

  • 普段はmedium、軽い定型作業はlow、難しい設計やバグ調査はhigh
  • 計画時だけ深く考えさせる設定もできる

推論を深くするほど時間とトークンを消費します。作業の難しさに合わせて切り替えます。

プロファイルで切り替える

会社用・個人用・検証用

使いどころ・ポイント

  • モデルや承認方針など複数の設定を1つの名前で束ねる
  • 起動時にプロファイル名を指定して丸ごと切り替える
  • 会社のリポジトリでは承認を厳しめにする

設定ファイルを毎回手作業で書き換える必要がなくなります。

ステータスライン

/statusline

表示できる情報

  • コンテキスト残量
  • モデル・推論レベル
  • Gitブランチ・作業ディレクトリ

使いどころ・ポイント

  • 残量を見て、上限に達する前に作業を区切る

長い対話でも、重要な指示を見失う前に/compactや新しいセッションへ切り替えやすくなります。

ターミナルタイトルと通知

複数セッション・長い処理

使いどころ・ポイント

  • タイトルを作業内容に合わせて変え、タブを見るだけでセッションを区別する
  • ビルドやテストなど長い処理の完了を、自作の通知スクリプトで受け取る

通知が多すぎると集中を妨げるため、本当に必要な種類だけに絞ります。

機能の有効化と書き方

機能フラグとマルチエージェント

[features] / [agents]

設定例

  • [features]
multi_agent = true
hooks = true

[agents]
max_concurrent_threads_per_session = 4

使いどころ・ポイント

  • サブエージェントやHooksを使うときに有効化する
  • 同時に動かすスレッド数の上限を決める

multi_agent = trueをトップレベルに書いたり、同じテーブルを離れた場所で再定義したりしないよう注意してください。

環境変数・履歴・信頼するプロジェクト

[shell_environment_policy] ほか

設定例

  • [shell_environment_policy]
inherit = "all"

[history]
persistence = "save-all"

[projects."C:/work/project"]
trust_level = "trusted"

使いどころ・ポイント

  • テーブル名はドットで階層を表す
  • パスなど記号を含むキーは引用符で囲む

古い設定例をそのままコピーせず、使っているCodexのバージョンで対応しているか公式ドキュメントで確認してから追加します。

利用枠を節約する

トークン消費を抑える7つの方法

設定 ＋ 運用

方法

  • モデルのグレードを下げる
  • 高速モード（Fast Mode）を避ける
  • 起動するディレクトリの階層に注意する
  • AGENTS.mdを短くする
  • サブエージェント（並列処理）は必要なときだけ使う
  • プロンプトで読む範囲を具体的に指示する
  • タスクごとにセッションを分ける

利用枠（Usage Limit）とコンテキストウィンドウは別物です。どちらを節約したいのかを意識して使い分けます。

config.tomlの置き場所

Codexの設定は~/.codex/config.toml（Windowsでは%USERPROFILE%\.codex\config.toml）で管理します。プロジェクト用の設定は<project>/.codex/config.tomlに置けます。すべてを一度に設定する必要はありません。気になる設定を1つ追加し、実際の作業で使いながら調整していきます。

プラグインの導入と注意点

プラグインは、Skills・Hooks・コマンド・外部連携などをまとめて追加する拡張機能です。/pluginsから検索してInstallし、外部サービス連携は初回に認証します。スキル単体なら、組み込みのスキルインストーラーに欲しい機能を伝えて追加することもできます。外部から取得したプラグインやスキルには、危険な命令や情報を盗む仕組みが含まれる事例が報告されています。公式カタログや実績のある定番を中心に選び、出所の分からないものは中身を確認してから導入してください。

CODEX / SKILLS

CodexのSkills一覧

Skillの作り方

最小構造のSkill

SKILL.md

記載例

  • ---
name: react-review
description: ReactのTSX/JSXをレビューするときに使う。VueやSvelteのときは使わない。
---
# 使う条件
React コンポーネントの変更をレビューするとき

# 手順
1. 変更されたTSX/JSXを確認する
2. レビュー観点に沿って指摘する

使いどころ・ポイント

  • フロントマターに名前と説明、本文に「使う条件」と「手順」を書く
  • 参考スクリプトや例文は、必要になってから追加する

毎回チャットに貼っているレビュー観点や作業手順は、Skillにすると誰がいつ使っても同じ品質で再利用できます。

説明文で発火条件を絞る

description

良い例・悪い例

  • 良い例：「ReactのTSXやJSXを触るときに使う。VueやSvelteのときは使わない」
  • 悪い例：一般的すぎる説明（毎回発火してしまう）

使いどころ・ポイント

  • 「いつ使うか」と「いつ使わないか」の両方を書く

Codexは説明文を読んでSkillを使うかどうかを判断するため、自動発火の精度は説明文で決まります。

補助スクリプト付きのSkill

scripts/

構成例

  • my-skill/
├── SKILL.md
├── scripts/      # 自動処理用スクリプト（例: check.js）
├── references/   # Skillが参照する資料
└── assets/       # テンプレートなど

使いどころ・ポイント

  • 本文に「scripts/check.js をNodeで実行する」のように書く
  • Lintや独自チェッカーをSkillに組み込む

SKILL.md以外のフォルダーは任意です。必要になったものから追加します。

$skill-creatorで作らせる

$skill-creator

使い方の例

  • $skill-creatorを実行し、「Create a skill for creating software requirements documents.」のように依頼する

使いどころ・ポイント

  • ひな型をゼロから設計せず、生成されたSKILL.mdをプロジェクトに合わせて調整する

何をするか・いつ使うか・どんな手順か・スクリプトが必要か、を整理しながら作成してくれます。

置き場所と共有

個人用とチーム用の使い分け

グローバル / リポジトリ

置き場所

  • ~/.codex/skills：自分の手癖・個人向けのSkill
  • リポジトリ内のSkillフォルダー：チーム全員に守らせたい作法（記事により.codex/skills・.agents/skillsの例があります）

使いどころ・ポイント

  • 同じ名前のSkillをグローバルとリポジトリの両方に置かない

どちらが優先されるかで問題が起きるため、用途で置き場所を分けます。導入状況は/skillsで確認できます。

チームで共有する3パターン

共有範囲で選ぶ

方法

  • 1リポジトリだけ：リポジトリにSkillフォルダーを置いてコミット
  • 複数リポジトリ：プラグインとしてパッケージ化して配布
  • 組織全体：社内のSkillカタログ（組織レジストリ）から配信

共有範囲と更新頻度のバランスで選びます。

Skillsの基本

Skillは、繰り返す作業の手順や知識をまとめた「AIに読ませるレシピ」です。Agentが「誰が担当するか」を決めるのに対し、Skillは「どうやって作業するか」を決めます。最初から複雑なSkillを作らず、1ファイルの最小構造から始め、条件・スクリプト・共有方法を少しずつ広げていきます。外部から取得したSkillは、中身を確認してから導入してください。

CODEX / MCP

CodexのMCP設定一覧

接続と確認

MCPサーバーを登録する

codex mcp add

実行例

  • codex mcp add <サーバー名> -- <起動コマンド>
codex mcp list

使いどころ・ポイント

  • サーバー名と起動コマンドを渡して登録する
  • codex mcp listで接続中のサーバーを確認する
  • セッション中は/mcpで使える状態かを確認できる

最初から多数のツールを接続せず、毎日使うツールを1つ接続するところから始めます。

config.tomlで設定する

[mcp_servers.<名前>]

設定例

  • [mcp_servers.github]
url = "https://example.com/github-mcp"
bearer_token_env_var = "GITHUB_TOKEN"
enabled = true

使いどころ・ポイント

  • トークンは設定ファイルに直接書かず、環境変数名で指定する
  • 使わないサーバーはenabled = falseで無効化する

URLは例です。実際の接続先は各MCPサーバーの公式ドキュメントで確認してください。

認証が必要なMCP

ブラウザでのログイン

流れ

  • Codexから認証を開始するとブラウザが起動する
  • サービスの同意画面で許可する
  • トークンが手元に保存され、次回以降は自動で認証される

GitHubやSlackのようにユーザー認証が必要なサービスでは、初回のログインフローを理解しておきます。

つながらないときの診断

codex mcp get

確認できること

  • サーバーごとの状態
  • 起動結果
  • 最後のエラーメッセージ

よくある原因

  • 起動コマンドの書き間違い
  • 必要な環境変数の設定不足

症状と切り分けの観点をパターン化しておくと、トラブル解決が速くなります。

安全に使う

STDIOとHTTPの使い分け

トランスポート

方式

  • STDIO：Codexがツールを起動し、標準入出力でやり取りする。手元で完結する軽いツール向け
  • HTTP：常駐しているサーバーにネットワーク越しに接続する。複数の端末で共有したい場合向け

許可リストでツールを絞る

ツールの許可リスト

使いどころ・ポイント

  • 1つのMCPサーバーが公開する多数のツールのうち、使うものだけを名前で許可する
  • 削除・送信など意図せず実行されたくない操作は許可しない

利用するツールを設定側で絞ると、破壊的な操作を防げるため自動化を任せやすくなります。

MCPとApps / Connectorsの使い分け

連携方式

方式

  • MCP：自分でサーバーを立てて直接つなぐ。独自ロジックを細かく仕込みたい場合
  • Apps / Connectors：運営側が用意した接続口。代表的なツールに手軽につなぎたい場合

自由度と運用の負担のバランスで選びます。

MCPの基本

MCPは、Codexを外部のツールやサービスにつなぐ仕組みです。codex mcp addで登録し、codex mcp list・/mcpで確認、codex mcp getで診断します。書き込みや送信ができるツールは許可リストで絞り、トークンなどの秘密情報は環境変数で管理してください。

CODEX / SUBAGENTS

CodexのSubagents（Custom Agent）一覧

Custom Agentの作り方

Architect Agent

.codex/agents/architect.toml

定義例

  • name = "architect"
description = """
Software architect responsible for requirements,
architecture, API design and database design.
"""
model_reasoning_effort = "high"
sandbox_mode = "read-only"
developer_instructions = """
You are the software architect for this project.
- analyze requirements
- create and update design documents
- identify contradictions between requirements and architecture
Do not implement application code unless explicitly requested.
"""

使いどころ・ポイント

  • name・description・developer_instructionsは最低限定義する
  • 設計担当はsandbox_mode = "read-only"でコードを書き換えさせない

特に重要なのはdescriptionです。Codexが「どのAgentに任せるか」を判断する材料になるため、担当範囲を明確に書きます。

Review Agent

レビュー専門

役割の例

  • バグ・セキュリティ問題・コーディング規約違反・テスト不足の検出
  • 結果をreview-report.mdに出力

禁止事項の例

  • ソースコードを直接変更しない
  • 問題のないコードを不必要に変更しない

レビュー方法や観点を毎回判断させず、役割を限定することで結果が安定します。

Builder / Tester

実装担当・テスト担当

役割の例

  • Builder：implementation・refactoring・migration などのSkillを使って実装する
  • Tester：テスト仕様書の作成とテストの実行

使いどころ・ポイント

  • developer_instructionsに、どのSkillを使うべきかを明示する

Agentは「誰が担当するか」、Skillは「どうやって作業するか」と分けて考えると設計しやすくなります。

構成と運用

Main AgentとSubagent

Orchestrator ＋ 担当Agent

役割

  • Main Agent：作業を分解し、適したAgentへ委譲して全体を管理する
  • Subagent：Main Agentから渡された限定的な仕事を処理する

タスクの渡し方の例

  • ×「プロジェクトを改善してください」
  • ○「src/parser配下を解析し、YAML解析処理の問題点だけを報告してください。ファイルは変更しないでください。」

Subagentには、境界のはっきりしたタスク（Bounded Task）を渡します。

プロジェクト構成

Agent と Skill の置き場所

構成例

  • my-project/
├── .codex/
│   ├── config.toml
│   └── agents/
│       ├── architect.toml
│       ├── builder.toml
│       ├── tester.toml
│       └── reviewer.toml
└── .agents/
    └── skills/
        ├── requirements/SKILL.md
        └── code-review/SKILL.md

使いどころ・ポイント

  • プロジェクト用は<project>/.codex/agents/、共通用は~/.codex/agents/

プロジェクト固有のAgentはリポジトリと一緒に管理すると扱いやすくなります。

並列実行の注意点

[agents]

使いどころ・ポイント

  • 依存関係のない調査・解析・テスト作成・レビューを並列で進める
  • max_concurrent_threads_per_sessionで同時実行数を制限する
  • Agentを増やしすぎない

並列実行するとAgentごとにコンテキストを消費するため、トークン使用量が増えます。必要なときだけ使います。

Subagentsの基本

Codexでは複数のAgentに作業を分担できます。Custom Agentは役割・指示・モデル・推論レベル・権限などを調整したAgentで、TOMLで定義します。使う前にconfig.tomlの[features]でmulti_agent = trueを有効にし、/agentsで確認します。AGENTS.mdは「守るべきルール」、Custom Agentは「担当者」、Skillは「作業手順」と役割を分けてください。

CODEX / APPROVAL & SANDBOX

Codexの承認・サンドボックス設定一覧

サンドボックス（どこまで触れてよいか）

read-only

sandbox_mode = "read-only"

設定例

  • sandbox_mode = "read-only"

使いどころ・ポイント

  • ファイルを書き換えず、読むだけに限定する
  • 設計レビュー・原因調査・他人のコードを安全に読ませたいとき

「問題点を調査してほしいが、ファイルは変更しないでほしい」作業に向いています。

workspace-write

sandbox_mode = "workspace-write"

設定例

  • sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = false

使いどころ・ポイント

  • 作業ディレクトリの中だけ書き換えられる
  • 外部ネットワークは遮断し、ソースコードや鍵が外に出る経路を閉じる
  • 依存パッケージの取得など必要なときだけnetwork_access = true

read-onlyでは作業が進まず、danger-full-accessは危険すぎるため、その中間の「日常の正解」とされています。

danger-full-access

sandbox_mode = "danger-full-access"

設定例

  • sandbox_mode = "danger-full-access"

使いどころ・ポイント

  • 読み書き・ネットワークの制限を外す最終手段
  • 捨ててもよい隔離環境・開発専用VMでのみ使う

1つの削除コマンドで本番DBを復旧できなくする事故も起こり得ます。常用せず、使い終わったら必ず元の設定に戻してください。

writable roots

writable_roots

設定例

  • [sandbox_workspace_write]
writable_roots = ["C:/work", "C:/temp"]

使いどころ・ポイント

  • 書き込んでよいディレクトリを明示的に並べる
  • 隣のリポジトリやホーム直下などへの誤書き込みを防ぐ

workspace-writeよりさらに厳密に書き込み範囲を絞りたいときに追加します。

承認モード（いつ人間に確認するか）

on-request

approval_policy = "on-request"

設定例

  • approval_policy = "on-request"

使いどころ・ポイント

  • 危険な操作のときだけ承認を求める
  • 日常の開発作業の初期値

毎回確認される煩わしさと、まったく確認されない怖さの中間です。

never

approval_policy = "never"

設定例

  • approval_policy = "never"

使いどころ・ポイント

  • 承認を一切求めない
  • CIや無人のバッチ処理で使う

approval_policy = "never"だけでPC全体を操作できるわけではなく、実際に操作できる範囲はサンドボックスが決めます。開発機での常用は安全弁を外すことになるため注意してください。

組み合わせの例

基本セット

日常の開発

設定例

  • approval_policy = "on-request"
sandbox_mode = "workspace-write"

使いどころ・ポイント

  • AGENTS.mdと合わせた3点セットで運用する
  • さらに範囲を絞りたいときだけwritable rootsを追加

「暴走」と「過剰な確認」の両方を避け、速度を落とさずに運用できる組み合わせです。

承認を減らしてサンドボックスは残す

VS Codeでの長時間作業

設定例

  • approval_policy = "never"
sandbox_mode = "workspace-write"

使いどころ・ポイント

  • 承認待ちで止まらずに実装・テストを進めさせる
  • 操作範囲はサンドボックスで制限したまま

承認をなくしたいならapproval_policy、操作範囲を広げたいならsandbox_modeと、分けて設定します。

自律実行を最優先

隔離環境・開発専用VMのみ

設定例

  • approval_policy = "never"
sandbox_mode = "danger-full-access"

使いどころ・ポイント

  • 無人で自律実行させる
  • 通常のPCでは使わない

承認なし＋広範囲なアクセスになるため、OSへの影響範囲が大きくなります。

承認・サンドボックスの基本

Codexの権限は、承認モード（approval_policy：確認するか）とサンドボックス（sandbox_mode：どこまで実行できるか）の2つのダイヤルで決まります。設定はconfig.tomlに書き、セッション中は/permissionsで切り替え、/statusで現在の状態を確認できます。最初は狭い範囲から始め、必要な範囲だけを明示的に広げてください。

スラッシュコマンドの基本

Codexのセッションで/を入力すると、使えるコマンドの候補が表示されます。すべてを暗記せず、「何をしたいか」から選べるようにしておくのがコツです。よく使う流れは、/planで計画 → 実装 → /diffで変更確認 → /reviewでレビュー、長い作業では/compact、後日の再開は/resumeです。
